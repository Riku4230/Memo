# 共通の作業ルール

このファイルは、りくの複数のリポジトリで同じ内容に保つ。アプリの名前、ディレクトリ、使用している技術、接続先のリソースは書かない。それらを書く場所は各リポジトリの `AGENTS.md` と `package.json` の scripts。

ルールの意味が変わる変更をしたら、上の `harness-version` を 1 つ上げる。

## リポジトリ間で揃えるファイル

次のファイルは、対象のすべてのリポジトリで同じバイト列にする。

- `docs/harness/common.md`
- `docs/harness/review.md`
- `docs/harness/lessons.md` の見出しと表の形（表に足した行はそのリポジトリの記録なので、他へコピーしない）
- `.github/ISSUE_TEMPLATE/` 以下のすべてのファイル
- `.github/pull_request_template.md`
- `.github/workflows/ci.yml`
- `.github/workflows/deploy.yml`

`ci.yml` のジョブは `check` と `e2e`。`check` は `typecheck`、`lint`、`test`。`e2e` はプルリクエストのときだけ動き、`npm run test:e2e` でローカルのサーバーに対して主な画面を撮る。画像は成果物 `e2e-screenshots` に残し、同じ PR のコメントを更新して、その成果物へリンクする。公開の画像置き場には置かない。それ以外の確認は、リポジトリ固有のワークフローに分ける。

`CLAUDE.md` は `AGENTS.md` を読む、という案内だけにする。

公開方法の違いは `package.json` の `build` と `deploy` に書く。画面の起動方法の違いは `test:e2e` に書く。ワークフローから呼ぶスクリプト名は `typecheck`、`lint`、`test`、`test:e2e`、`build`、`deploy` だけにする。

## ハーネスを変えるとき

X などで見つけた、エージェントの進め方や CI・テスト・手順書の改善は、機能追加やバグではなく「ハーネス改善」の Issue にする。ラベルは `harness`。出典の URL を書く。

共通ファイルを直すときは、片方のリポジトリだけにしない。同じ内容を、対象のすべてのリポジトリの PR にする。アプリ固有の手順を共通ファイルへ移さない。

ラベル `feature`、`bug`、`harness` がリポジトリに無いと Issue テンプレートのラベルは付かない。無いときはオーナーが一度だけ作る。

## チケットの進め方

1. Issue を読み、完了条件を自分の言葉で箇条書きにする。曖昧なところは、実装の前に質問する。
2. 既定ブランチから作業ブランチを作る。
3. 完了条件の範囲だけ直す。関係ない整形やリネームを混ぜない。
4. 本番データ、秘密情報、公開設定には触らない。判断に迷ったら止めて質問する。
5. `npm run typecheck`、`npm run lint`、`npm run test` を実行し、成功させる。画面を変えたときは `npm run test:e2e` も実行する。
6. PR は `.github/pull_request_template.md` に沿って書く。画面を変えたときはスクリーンショットを添える。
7. 再発しそうなことを `docs/harness/lessons.md` に 1 行足す。足すことが無ければ行は増やさない。`AGENTS.md` に書くべきことがあれば、同じ PR に含める。
8. マージはオーナーが行う。マージ後の本番公開はワークフローが行う。自分で本番へ出さない。

## 完了の定義

- Issue の完了条件を満たしている
- `npm run typecheck`、`npm run lint`、`npm run test` が成功している
- PR に、実行したコマンドとその結果が書いてある
- 画面を変えた PR には、その画面のスクリーンショットがある。CI の `npm run test:e2e` が主な画面を撮り、PR のコメントから成果物へリンクする。変えた箇所がそれで分からないときは、PR 本文にも画像を足す。画面に関係しない変更は「なし」と書いてある
- 秘密情報や個人の記録が、コード、PR、Issue、ログ、スクリーンショットに含まれていない
- `docs/harness/lessons.md` を確認し、再発しそうなことがあれば 1 行足してある
- `AGENTS.md` を更新したか、更新不要かを PR に書いてある

## 秘密情報と個人のデータ

これらのリポジトリのアプリには、個人の記録が入る。

- 秘密情報をコミットしない。`.env`、`.dev.vars`、鍵、トークン、証明書、バックアップ、エクスポートしたデータが対象
- 値は、ホスティング側と GitHub の Settings の Secrets にだけ置く。チャット、Issue、PR、ログに貼らない
- スクリーンショットに秘密情報や個人の記録が写っていたら、貼る前に隠す
- 漏れたら、発行元で無効化し、新しい値を入れ直す。古い値を残さない
- テストやサンプルに、本物の記録を使わない
- ワークフローに秘密情報の値を書かない。公開に必要な Secrets が無いときは、失敗させずにスキップする

## 頼まれずに触らないもの

次は、Issue に明示されていない限りやらない。

- 本番データの読み出し、書き換え、削除、復元、マイグレーション
- 秘密情報の登録、削除、表示、ファイルへの書き出し
- 本番への公開、公開の条件、接続先のリソースの変更
- 利用者が戻しにくい、破壊的なデータ変更

ローカルの開発用データと、テストが自分で作るデータは、この限りではない。
