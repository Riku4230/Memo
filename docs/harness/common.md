# ハーネス共通ルール

このファイルは複数のリポジトリで同じ内容にする。アプリの名前、ディレクトリ、技術の名前は書かない。それらは各リポジトリの `AGENTS.md` に書く。

作業を始める前に、このファイルと、そのリポジトリの `AGENTS.md` を読む。

## 共有するファイル

次のファイルはリポジトリ間で揃える。変えるときは「ハーネス改善」のチケットにし、共有しているすべてのリポジトリへ同じ変更を入れる。アプリの機能追加やバグ修正の PR に、共有ファイルの変更を混ぜない。

- `docs/harness/common.md`（このファイル。変えたら先頭の `harness-version` を 1 つ上げる）
- `docs/harness/review.md`
- `docs/harness/lessons.md` の見出しと表の書式。表より下の記録行はリポジトリごとに違う。同期するときに、他のリポジトリの記録行を消したり上書きしたりしない
- `.github/ISSUE_TEMPLATE/`
- `.github/pull_request_template.md`
- `.github/workflows/ci.yml`
- `.github/workflows/deploy.yml`

ワークフローは次の npm script だけを呼ぶ。

- `npm run typecheck`
- `npm run lint`
- `npm run test`
- `npm run test:e2e`
- `npm run build`
- `npm run deploy`

スタックごとのコマンドの中身は、そのリポジトリの `package.json` に置く。

`npm run test:e2e` は、ローカルの開発サーバーに対して Chromium だけで主要な画面を開き、PNG を `e2e/screenshots/` に書く。CI はそのディレクトリを成果物 `e2e-screenshots` として上げる。プルリクエストでは、同じコメントを更新し、実行へのリンクとファイル名を書く。成果物の URL は認証がないと開けないため、画像そのものはコメントに埋め込まない。

## チケットの進め方

1. Issue を読む。背景、やりたいこと、完了条件、テスト方法が揃っていなければ、実装の前に Issue へ質問を書き、足りないものを埋めてもらう。
2. 完了条件を満たす範囲だけを変える。頼まれていない整理や、関係ないファイルの書き換えを混ぜない。
3. ブランチを切り、完了条件に沿って実装する。
4. `npm run typecheck`、`npm run lint`、`npm test` を実行し、失敗を残さない。画面を変えたときは `npm run test:e2e` も成功させる。
5. 画面を変えたときは、CI がプルリクエストに残すスクリーンショットでその画面が分かるようにする。スモークが撮らない画面は、PR 本文にも画像を付ける。
6. PR はテンプレートに沿って書く。検証したことは、実行したコマンドと結果を書く。実行していないことを、通ったとは書かない。
7. つまずきや、次も踏みそうなことがあれば `docs/harness/lessons.md` に 1 行足す。同じ PR で `AGENTS.md` に残すべき恒久的な決まりがあれば、それも入れて提案する。学びがなければ lessons には何も足さない。
8. マージはオーナーが行う。エージェントはマージしない。本番への公開は、マージされたあとの自動デプロイに任せる。手元やプルリクエストから本番へ出さない。

## 完了の定義

- Issue の完了条件を満たしている
- `npm run typecheck`、`npm run lint`、`npm test` が成功している。画面を変えたときは `npm run test:e2e` も成功している
- PR に、実行したコマンドとその結果が書いてある
- 画面を変えた PR では、CI のスクリーンショット（成果物 `e2e-screenshots` と、プルリクエストのコメント）にその画面が写っている。スモークの対象外は PR 本文の画像で補う
- シークレットや本番データが diff、ログ、スクリーンショット、PR の本文に含まれていない
- 共有ファイルを変えたときは、ハーネス改善として、共有しているすべてのリポジトリに同じ変更を入れる

## シークレットとデータ

- トークン、パスワード、鍵、接続文字列をコミットしない。ログ、スクリーンショット、Issue、PR の本文にも書かない。説明が必要なときは、値の代わりにプレースホルダを使う。
- ローカルだけで使う設定ファイルをコミットしない。
- 本番のデータを取り出して、リポジトリ、PR、ログ、チケットに置かない。個人の記録が含まれる。
- 本番のデータを消す、上書きする、過去の時点に戻す操作は、チケットにその操作が書いてあり、オーナーが頼んだときだけ行う。

## 頼まれずに触らないもの

- 本番データ
- 本番に対するマイグレーション、および本番のスキーマを変える操作
- シークレットの値。シークレットを新しく作ること、入れ替えること、消すこと。名前と、オーナーが自分で登録する手順をドキュメントに書くのはよい
- 本番へ公開する設定。公開先、本番の資源の ID、本番デプロイが走る条件。変える必要があればハーネス改善のチケットにする
- 上の「共有するファイル」。アプリのチケットのついでに変えない

## ハーネスを変えるとき

1. 「ハーネス改善」の Issue を作る。アイデアの元になった URL があれば出典に書く。
2. 完了条件に、どの共有ファイルをどう揃えるかを書く。
3. `docs/harness/common.md` を変えたら、先頭の `harness-version` を 1 つ上げる。
4. 同じ差分を、このハーネスを共有しているすべてのリポジトリに入れる。
5. アプリ固有のことは `AGENTS.md` に書き、共有ファイルには置かない。

## ラベル

Issue とプルリクエストでは次のラベルを使う。

- `feature` — 機能追加
- `bug` — バグ
- `harness` — ハーネス改善（このファイル、CI、テストの仕組み、エージェントの作業手順）
